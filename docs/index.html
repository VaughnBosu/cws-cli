Shared setup

Configure credentials once.

The CLI creates the OAuth credentials used by both projects. Keep secrets in the global config and commit only extension settings to the project.

1

Install the CLI

Homebrew installs the versioned binary release on macOS or Linux.

brew install --cask vaughnbosu/tap/cws
2

Create global credentials

The browser-based flow saves secrets outside your repository.

cws init --global
3

Add the project profile

Create cws.toml beside your extension source.

[extensions.default]
id = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
source = "./dist"

Before setup, enable Chrome Web Store API access and create desktop OAuth credentials by following Google’s official API guide.

cws CLI

From preflight to rollout.

Validate locally, compare against the store, package cleanly, upload, publish, and inspect the result without leaving your terminal.

github.com/vaughnbosu/cws-cli ↗

A typical release

Validation runs automatically before upload. Publish separately when you want the release boundary to stay explicit.

# Local + remote preflight checks
cws validate ./dist

# Package and upload
cws upload ./dist

# Submit the latest upload
cws publish

Command reference

Store and packaging commands accept --json. Select a named profile with --ext <name>.

cws init [--global]Configure OAuth credentials and publisher settings
cws loginRe-acquire a refresh token in the browser
cws validate [source]Check manifest, icons, size, versions, and store state
cws pack [source]Create a clean extension ZIP without uploading
cws upload [source]Validate, package, upload, and wait for processing
cws publishSubmit the latest uploaded version
cws statusRead published and submitted state, warnings, and takedowns
cws rollout <percentage>Adjust a partial rollout for eligible extensions
cws cancelCancel a pending submission
cws versionPrint the installed version

Useful variations

Validation 
cws validate ./dist          # local + store checks
cws validate ./dist --local  # no credentials required
cws validate extension.zip   # pre-built package
Publishing 
cws publish --staged
cws publish --skip-review
cws publish --block-on-warnings
cws publish --deploy-percentage 10
Machine-readable output 
cws status --json
cws upload ./dist --json

GitHub Actions

Pin both the Action and binary version for repeatable releases.

- name: Upload and publish extension
  uses: vaughnbosu/cws-cli@v1.3.1
  with:
    version: v1.3.1
    args: upload ./dist --publish
    client-id: ${{ secrets.CWS_CLIENT_ID }}
    client-secret: ${{ secrets.CWS_CLIENT_SECRET }}
    refresh-token: ${{ secrets.CWS_REFRESH_TOKEN }}
    publisher-id: ${{ secrets.CWS_PUBLISHER_ID }}
    extension-id: ${{ vars.EXTENSION_ID }}

The Action supports GitHub-hosted Linux and macOS runners on amd64 or arm64. The CLI also ships Windows binaries.

Install the server

The MCP binary runs locally over stdio. It reads the same global credentials and project profiles as the CLI.

brew install --cask vaughnbosu/tap/cws-mcp

Codex

Add this to ~/.codex/config.toml. The CLI, IDE extension, and desktop app share this configuration.

[mcp_servers.chrome-web-store]
command = "cws-mcp"
default_tools_approval_mode = "writes"

[mcp_servers.chrome-web-store.env]
CWS_WORKSPACE = "/absolute/path/to/extension"

Run codex mcp list, then use /mcp in a session to inspect the connection.

Claude Code

Create a machine-local entry so the absolute workspace path is not committed.

claude mcp add --transport stdio --scope local \
  chrome-web-store \
  --env CWS_WORKSPACE=/absolute/path/to/extension \
  -- cws-mcp

Cursor, Claude Desktop, or Windsurf

Place this mcpServers entry in the client’s MCP config. GUI clients may need the full binary path from command -v cws-mcp.

{
  "mcpServers": {
    "chrome-web-store": {
      "command": "cws-mcp",
      "env": {
        "CWS_WORKSPACE": "/absolute/path/to/extension"
      }
    }
  }
}

VS Code with Copilot

VS Code uses servers, not mcpServers, and requires the stdio type.

{
  "servers": {
    "chrome-web-store": {
      "type": "stdio",
      "command": "cws-mcp",
      "cwd": "${workspaceFolder}",
      "env": { "CWS_WORKSPACE": "${workspaceFolder}" }
    }
  }
}

Tools and safety boundaries

The client can inspect auth, config, packages, and store state. Store mutations require an explicit confirm: true argument.

Read and prepare

check_auth, get_setup_instructions, list_extension_profiles, get_extension_status, validate_extension, pack_extension

Confirmed writes

upload_extension, publish_extension, set_rollout_percentage, cancel_submission

Release tools inside your AI workflow.

Configuration

Secrets stay global. Projects stay portable.

Both binaries resolve the same TOML files and environment variables. The MCP server additionally confines source and output paths to CWS_WORKSPACE.

Resolution priority

The first value found wins.

  1. Command flags such as --extension-id
  2. Environment variables prefixed with CWS_
  3. Project ./cws.toml
  4. Global ~/.config/cws/cws.toml

Environment variables

Useful in CI or when file-based credentials are not appropriate.

CWS_CLIENT_ID
OAuth client ID
CWS_CLIENT_SECRET
OAuth client secret
CWS_REFRESH_TOKEN
OAuth refresh token
CWS_PUBLISHER_ID
Chrome Web Store publisher ID
CWS_EXTENSION_ID
Default extension ID override
CWS_WORKSPACE
MCP project root and path boundary
